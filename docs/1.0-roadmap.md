# truss 1.0 roadmap {#roadmap_page}

**Current:** v1.0.0 — tagged. All thirteen phases of `PLAN.MD` are complete
and the build *engine* is feature-complete: targets, globbing, usage
requirements, C++20/26 modules (full transitive BMI closure + `import std` on
clang+libc++ and GCC 15+), static linking, zig cross-compilation, mingw
Linux→Windows cross builds, per-triple subgraphs, `fetch`/`conan`/`vcpkg`,
MSVC flag mapping, hardening tiers, a performance phase, merged archives, and
a self-rebuilding `./truss` that tracks its own headers and BMIs. The public
API is frozen behind semver (see CHANGELOG.md).

This file now tracks what is *post*-1.0. Companion roadmap for the
cross-compilation axis: `docs/cross-compilation.md` (phases 1–5).

---

## P0 — 1.0 blockers

A general-purpose C++ build tool cannot call itself 1.0 while it only runs on,
and only targets, part of the mainstream C++ world.

1. **Windows host support.** truss itself is POSIX-only (`src/core/proc.cpp`
   uses `posix_spawn`/pipes; `self_exe`, `temp_scope`, the self-rebuild `sh
   bootstrap.sh` path all assume POSIX). Port process spawning, path handling
   and the bootstrap flow to run `./truss` natively on Windows.
2. **Real MSVC validation.** The clang-cl / `cl.exe` path builds an `.exe` and is
   unit-tested via dry-run manifests, but has **never been run on Windows**.
   Validate compile + `/showIncludes` deps + link + run on a real MSVC target;
   extend static linking and modules support or document the gaps.
3. **macOS validation.** Mach-O naming, `-install_name`/`@loader_path` rpaths and
   the dylib path are coded but untested on real macOS. Add macOS CI, validate a
   build+run, and implement `-framework` / framework search paths.
4. **Public API freeze + semver.** Declare the `truss` module's public surface
   (the AGENT.MD §7 invariants) stable and commit to semantic versioning for
   1.x. Audit for anything we still want to change before locking it.

## P1 — strongly wanted for 1.0

5. **Cross-compilation phase 2 — host vs target (`for_host()`).** Code generators,
   embedders and protoc plugins must build for the *host* during a cross build.
   Pin such targets to `host_triple()`, and make a host↔target `depends_on()`
   mismatch a Config error. (`docs/cross-compilation.md` §Phase 2.)
   **Shipped:** `Target::for_host()` pins to the host triple (Config compiler/
   stdlib/ar overlays still apply, the cross target never does); any
   `depends_on()` edge crossing the host/target boundary (or joining two
   different cross triples) is a Config error naming both sides; cross-compiled
   `is_test()` exes are built but skipped with a warning by `./truss test`
   (never silently "passed"), and `run` on a cross exe is a clear Config error.
   **Shipped (incl. the phase 2 tail):** `add_custom_command(...).uses(host_tool)`
   runs the tool at build time and feeds its outputs to consumers (implicit
   compile inputs + `-I` of the output dir); see `docs/cross-compilation.md`
   §Phase 2.
6. **Cross-compilation phase 3 — CLI + matrices + test runner.**
   **Shipped:** per-triple subgraphs — `proj.targets({{"linux", Config{}}, ...})`
   emits one subgraph per triple into the same manifest (one invocation,
   per-subgraph runners, `--for` / compound `--target name:subgraph`
   selection); `Config::runner("qemu-… / wine …")` executes cross-compiled
   `test`/`run` exes through a command prefix instead of skipping them.
   (The earlier `--cross` CLI override was removed — the subgraphs API
   supersedes it.)
7. **Imported prebuilt-library target (backlog #8).** **Shipped:**
   `proj.import_library(name).import_archive(path)...` — prebuilt `.a`/`.so`/
   `.dylib`/`.lib` files land verbatim on dependents' link lines (after their
   objects, GNU ld order, transitive via `depends_on`); include dirs propagate
   as usage requirements; an imported `.so`/`.dylib` adds an rpath to its
   directory; missing/unsafe paths are Config errors at `build()` time.
8. **Security hardening pass.** **Shipped:** post-extraction scan of fetched
   tarballs rejects any symlink whose target escapes the package dir (plus
   `--no-same-owner`, and the half-materialized tree is removed on refusal);
   git/curl option injection was already guarded. Remaining: audit other
   outward-facing surfaces as they appear.
9. **`/code-review` pass.** **Shipped:** branch-wide review — fixed swallowed
   `waitpid` failure and silently-dropped spawn `cwd` (proc.cpp), `--target`
   on artifact-less targets is now a Config error, cross test/run handling as
   in #5. Noted (deliberate, not changed): `log::error`+`return unexpected`
   boilerplate could collapse into one helper; per-edge flag-string copies.

## P2 — post-1.0 / stretch

### DX backlog (from the review pass)

- **`./truss why <target>`** — print the dependency path from `all` to a
  target (samurai already has the graph; it's a query over `by_name`).
- **Config error dedup helper** — `log::error(e); return std::unexpected(e);`
  repeats ~24× in build.cpp; one `fail_logged(e)` helper would declutter.
- **`proj.targets({...})` matrices** — one subgraph per triple in a single
  manifest (deferred: the emitter resolves one project triple today; see #6).
- **`import std;` beyond clang+libc++** and a real lexer for the module
  scanner — see items 12/13 below.

10. **Cross-compilation phases 4–5.** Packages follow the target triple
    (`vcpkg`/`conan`/`fetch` per-triple, `Config::sysroot`); portable truss
    releases. Phase 5 for truss *itself* is currently **blocked**: truss is
    module-based (can't build with zig), and the amalgam path hits (A) a
    zig-bundled-musl `realloc(NULL,0)==NULL` quirk in the vendored samurai
    (`xreallocarray` treats it as fatal) and (B) `posix_spawn_file_actions_addchdir_np`
    (glibc 2.29) below a 2.17 floor. See `docs/cross-compilation.md` §Phase 5.
11. **Sanitizers on cross targets.** zig ships no ASan/UBSan runtimes; needs a
    sysroot that provides them, or a documented "clang + sysroot" recipe.
12. **`import std;` beyond clang+libc++.** GCC (`std.cc` from libstdc++) and
    clang+libstdc++ support, if the toolchains expose a usable std module.
13. **Scanner robustness.** The v0.1 regex module scanner is line-anchored and
    conservative; consider promoting `modules_mode(Manual)` (clang-scan-deps) or
    a real lexer for edge cases, and relax the space/`:` path restrictions.

## Done this cycle (was backlog, now shipped)

- zig toolchain verified for real + unsupported-path guards (modules/PCH/manual).
- `import std;` / `import std.compat;` (clang + libc++).
- Full transitive module BMI closure (re-exported and indirectly imported).
- Self-rebuild tracks included headers and the truss library/BMIs (depfile-based).
- `merge()` — combine static archives into one (`ar -M`).
- `add_custom_command()` — run a (usually `for_host()`) tool during the build;
  outputs feed consumers as implicit compile inputs + include dir (`$tool`/`$out`/`$in`
  placeholders, default output `build/<mode>/gen/<name>/output`).
- `for_host()` — host-pinned tools in cross builds; host↔target `depends_on()`
  mismatch is a Config error; cross test exes build-then-skip with a warning.
- `Config::runner(...)` for executing
  cross-compiled test/run exes (phase 3 CLI + runner).
- `import_library()` — first-class imported prebuilt-library target
  (verbatim link-line files, usage requirements, rpath for imported `.so`).
- Deref-free `depends_on()`/`merge()` — `Result<TargetRef>` passes straight in.
- Fetch hardening — tarballs with escaping symlinks are refused; review fixes
  (waitpid/cwd in proc.cpp, `--target` on artifact-less targets).
